# План миграции хранения для Windows-приложения

## Цель

Перевести приложение на локальную Windows-архитектуру: Tauri 2, SQLite и файловое хранение медиа. Приложение должно работать офлайн, не терять подтверждённые изменения и быть готовым к будущей синхронизации между устройствами.

## Контракты первого этапа

- `TreeRepository`: атомарно сохраняет и загружает дерево, сообщает об ошибках записи и не допускает, чтобы более старая запись перезаписала новую.
- `MediaAttachmentService`: ручные привязки медиа к персонам независимы от тегов лиц; одно медиа может быть вручную связано с несколькими персонами.
- `BackupService`: принимает только валидные архивы, показывает состав перед заменой данных и не изменяет текущее дерево при ошибке импорта.

## Последовательность работ

1. Добавить регрессионные тесты для контрактов первого этапа на текущем TypeScript-слое. Выполнено.
2. Исправить текущие критические ошибки IndexedDB и медиа-синхронизации, не меняя пользовательский интерфейс. Выполнено.
3. Выделить доменные модели и интерфейсы трёх контрактов из React-компонентов. Частично выполнено: правила связей, медиа и нативный репозиторий имеют отдельные публичные функции.
4. Создать Tauri 2 оболочку и SQLite-репозиторий с миграциями. React обращается к узким командам приложения, а не к произвольному SQL. Выполнено: `load_tree` и `save_tree` используют SQLite в Tauri, браузер сохраняет IndexedDB-режим.
5. Перенести медиа из Base64 в файлы каталога приложения. SQLite хранит метаданные, контрольные суммы и ссылки; ручные привязки становятся отдельной таблицей. Выполнено: `data:`-контент сериализуется в каталог `media` рядом с БД и гидратируется при загрузке.
6. Добавить переносимый ZIP-бэкап: SQLite-база, каталог медиа и манифест версии. Выполнено: системный диалог сохранения, проверка во временном каталоге, подтверждение восстановления и автоматический rollback-ZIP.
7. Миграция старых IndexedDB-архивов не входит в локальный MVP: существующих пользовательских архивов нет.
8. Добавить журнал изменений и ревизии сущностей как подготовку к синхронизации. Серверная синхронизация остаётся отдельной последующей задачей.

## Целевая модель SQLite

- `persons`: данные персон и версии записей.
- `relationships`: направленные связи между персонами.
- `media`: метаданные файла, путь, MIME-тип, размер и контрольная сумма.
- `media_attachments`: явные ручные связи между персоной и медиа.
- `face_tags`: рамки, дескрипторы и подтверждённые назначения лиц.
- `changes`: журнал локальных изменений для будущего обмена с сервером.

SQLite создаёт `tree_snapshot` как резервный rollback-слой и в одной транзакции проецирует данные в целевые таблицы. Native read-path уже восстанавливает дерево из нормализованных записей.

## Правила данных

- Файл медиа существует в единственном экземпляре; привязки не копируют файл.
- Тег лица может создать предложенную привязку, но не может удалить ручную привязку.
- Операция считается сохранённой только после успешного завершения транзакции.
- Ошибка сохранения видна пользователю и оставляет данные доступными для повторной попытки или экспорта.
- Импорт заменяет данные только после полной валидации и явного подтверждения.

## Целостность файлов — выполнено

- Имена файлов формируются по SHA-256 содержимого; одинаковый контент с одинаковым типом хранится один раз.
- SHA-256 и фактический размер сохраняются в payload записи `media` как внутренние поля `sha256` и `fileSize`.
- При чтении проверяются наличие, размер и контрольная сумма файла.
- Очистка неиспользуемых файлов выполняется только после успешного коммита SQLite и учитывает все записи медиа, включая файлы без привязки к персоне.
- Ошибка загрузки блокирует редактирование, чтобы пустое дерево не заменило повреждённый архив.
- Rust-регрессии покрывают повреждение, отсутствующий файл, общий контент, очистку и отказ транзакции.

## ZIP-бэкапы — выполнено

- В Windows окно «Архив» сохраняет ZIP через системный диалог. Бэкап включает согласованный SQLite-снимок (`VACUUM INTO`), каталог `media` и `manifest.json`.
- Манифест содержит версию формата, размеры и SHA-256 всех файлов.
- При выборе ZIP проверяются пути, дубликаты, состав архива, контрольные суммы, версия SQLite, `integrity_check`, внешние ключи и содержимое медиа. Проверка выполняется во временной папке без замены текущего архива.
- После проверки показывается количество персон, связей и медиа; восстановление требует отдельного подтверждения. Отмена не меняет данные.
- Перед восстановлением текущий архив сохраняется в `backups/before-restore-<timestamp>.zip` рядом с БД. После успешного восстановления интерфейс перезагружается.
- Лимиты первой версии: 100 МБ ZIP, 512 МБ распакованного содержимого, не более 10 000 ZIP-записей.
- Сохранение, экспорт и восстановление сериализованы нативным mutex. Экспорт дополнительно сохраняет текущее состояние UI перед созданием копии.
- Автономность desktop-версии и нативный smoke-test выполнены (см. ниже).

## Автономность desktop — выполнено

- Google Fonts заменены локальными Fontsource Variable-файлами, включёнными в сборку.
- Модели распознавания загружаются только из `public/models`; CDN fallback удалён.
- `face-api` загружается динамически при распознавании. Сравнение готовых дескрипторов не требует нейросети.
- Стартовый JavaScript уменьшен с примерно 1,79 МБ до 487 КБ; отдельный нейросетевой модуль — около 1,31 МБ.
- Service Worker и манифест подключаются только в браузерном режиме. В Tauri старый worker приложения снимается, кнопка PWA не предлагается.
- Dev-сервер использует loopback и фиксированный порт.

## Проверки локального MVP

Нативный сценарий проверен через WebView2/CDP на отдельной debug-сборке с embedded frontend:

1. Сборка: `npx tauri build --debug --no-bundle --config src-tauri/tauri.smoke.conf.json`.
2. Запуск `src-tauri/target/debug/app.exe`. Smoke-конфигурация использует отдельный identifier и каталог `$TEMP/opencode/genedek-desktop-smoke`, порт CDP 9224. Не использовать её для обычного запуска или поставки.
3. Внешние HTTP-запросы заблокированы. Созданы персона и PNG через интерфейс. Все три нужных model manifests и bin-файлы загрузились локально с HTTP 200.
4. SQLite сохранила одну персону и один медиафайл. Создан ZIP через нативную команду экспорта.
5. Через интерфейс очищен тестовый архив, выбрана ZIP-копия и подтверждено восстановление. Персона и медиа восстановлены.
6. Процесс полностью закрыт и запущен повторно: персона и медиа сохранены; внешних запросов и зарегистрированных Service Worker нет.
7. Production MSI и NSIS собраны без smoke-конфигурации. Release-процесс запускается и отвечает.

Мастер установки MSI/NSIS в автоматическом smoke-сценарии не проходился: проверены упаковка, запуск release-бинарника и изолированный нативный сценарий данных.

## Базовые регрессионные тесты

Первая серия тестов зафиксировала дефекты исходного кода и теперь должна оставаться зелёной при последующих изменениях.

- `src/services/db.test.ts`: повреждённый архив с некорректной персоной отклоняется до замены данных.
- `src/services/db.test.ts`: связи с отсутствующими персонами и повторяющиеся идентификаторы персон отклоняются.
- `src/services/db.test.ts`: медиаархив с некорректными обязательными полями отклоняется.
- `src/services/db.test.ts`: неполные записи персон, вложенное медиа и неподдерживаемые типы связей отклоняются; встроенный демо-архив остаётся валидным.
- `src/services/db.test.ts`: ошибка записи IndexedDB возвращается вызывающему коду.
- `src/services/faceRecognition.test.ts`: ручная привязка нетегированного медиа сохраняется у каждой связанной персоны.
- `src/utils/relationships.test.ts`: удаление выбранной связи по ID не затрагивает другие связи той же пары.
- `src/services/faceRecognition.test.ts`: открепление медиа очищает тег во всех копиях, а ручная привязка не зависит от тегов лиц.
- `src/services/db.test.ts`: последовательные сохранения не могут завершиться в обратном порядке.
- `src/services/media.test.ts`: неподдерживаемые и слишком большие файлы отклоняются, а ошибка чтения файла возвращается вызывающему коду.

Следующие циклы TDD добавляют контракты по одному: глубокая валидация архива, последовательные записи, безопасное удаление связей и миграция в SQLite.
